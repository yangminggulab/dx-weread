# 多端日记同步设计与复盘

核对日期：2026-10-07。适用于 Apple 客户端、云端网页、微信小程序与 Worker。本文记录本次实现；源码、构建、安装和云端部署是不同状态，实际发布状态见各端 CHANGELOG / SETUP。本地 Python 日记库暂不支持此协议，继续使用受保护的按日期保存，不自动上传云端。

## 成熟产品给出的经验

官方资料表明，“自动同步”不等于“永远没有冲突”，更不等于直接覆盖正文。

- [Figma 的多人协作技术说明（2019）](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)介绍其属性同步与离线重连机制。属性级最后写入策略不能直接套用到整篇日记。
- [Figma Code Layers（2025）](https://www.figma.com/blog/building-figmas-code-layers/)说明整段代码的最后写入策略不够用，并介绍基于 Eg-walker 的文本协作。这支持一个工程判断：长期真实多人同时编辑需要操作级文本协议；不能把自动保存或时间戳比较称作 CRDT。
- [Google Docs 版本历史](https://support.google.com/docs/answer/190843?hl=en)支持查看并恢复历史版本。恢复能力应成为正常入口，而不是只在报错时暴露。
- [Microsoft OneDrive 同步排查](https://learn.microsoft.com/en-us/troubleshoot/sharepoint/sync/troubleshoot-sync-issues)区分 Office 与其他文件的处理；非 Office 文件可能保留双方副本。[Word 协作排查](https://support.microsoft.com/en-us/word/troubleshoot-common-coauthoring-errors)仍包含需要处理的合并冲突。
- [Dropbox 冲突副本](https://help.dropbox.com/organize/conflicted-copy)保留竞争修改，供比较处理。保留原文比静默覆盖更可靠。

以下方案是结合本项目的个人使用、短篇日记、低频多端切换、现有 SQLite Durable Object 选出的工程实现，不宣称复制上述产品的算法，也不宣称已实现实时协作 CRDT。

## 原问题与目标

原先正文保存依赖版本比较。浏览次数、标签等元数据改变也会改变时间戳，容易误报“云端有另一份更新”。保存成功但回执丢失后继续输入，又可能把自己刚上传的正文误判成其他人的冲突。直接删掉提示、按最后时间覆盖，都会失去保护。

目标：正常使用不要求用户二选一；正文修改可自动处理，所有参与正文可恢复；断网保留草稿，重试不重复执行旧保存。认证、存储、网络故障仍以简短状态提示，不能伪称保存成功。

## 统一策略

1. 输入立即保存到各端本机草稿。正文、原日期、已见正文基线和确认时间一起保留。按上海时间 05:00 切日，不把未上传的昨日草稿改成今日日期。
2. 新服务端在日记读取结果声明 `syncVersion: 1`。三端才使用 `POST /api/diary/sync`；不支持能力时继续原有受保护写入，不能退成无条件覆盖。
3. 每次发送前持久化不可变操作：`operationId / source / date / content / baseContent / baseUpdatedAt`。同一操作的重试沿用完整原始载荷，不能只保留 ID 却改变正文或基线。
4. 服务端比较正文，元数据沿用当前云端值。正文无变化、或一方仍等于基线时直接采用有修改的一方。对互不重叠的 Unicode 文本编辑作三方合并，保持原始空白、换行与主动清空。
5. 同处修改、基线未知、或大范围文本比较超过预算时不猜测句子。先原样保存当前正文、提交正文和可用基线，再采用本次提交作为当前正文；另一方可以在版本历史中恢复。此情况属于“版本保全”，不能写成“双方正文均已合并到当前正文”。
6. 版本快照、当前正文、操作回执在同一个 TaskState SQLite 事务内提交；任一备份或回执写入失败必须整体回滚。普通 KV 路径不声明能力、不接受此接口。
7. 回执验证操作 ID、原提交正文、日期和结果类型；合并后的正文允许与提交不同。回执丢失时同 ID 返回原回执，不能再次改变当前正文。旧回执只证明旧提交成功，客户端重新读取最新正文，不用旧回执覆盖已观察到的较新版本。
8. 普通并发正文变化不展示冲突卡；各端提供安静的“版本历史”入口。旧协议仍保留冲突卡，真实网络或存储错误仍保留草稿并重试。

## 不能遗漏的回执边界

保存时继续输入：A 是已提交文字，R 是另一端新增文字，服务端回执是 `merge(A, R)`，此时本机已输入 B。B 的下一次基线必须是 A，而不是 `merge(A, R)`。否则 B 中尚未出现的 R 会被误解为用户主动删除 R。本次三端都保留 B，以 A 推进正文基线，仅使用回执推进确认时间。

较旧的排队操作在网页实际发送前已被新输入取代时，可跳过旧上传，保留并随后保存最新草稿。旧页面回执不能清除新页面接管的草稿。恢复版本之前必须确认当前草稿已保存；恢复本身也先落本机操作，再上传，失败后可以重新打开或返回编辑器继续恢复。

主动清空与遗留空草稿分开识别。Apple 的版本恢复标记和已持久化操作不能被旧版空草稿清理逻辑删除。显式 `baseContent: null` 表示基线未知或完整版本恢复，不能序列化成缺失字段。

## 数据与接口

| 位置 / 接口 | 职责 |
|---|---|
| `worker/src/diary-sync.mjs` | 有预算的 Unicode 三方合并、原文版本、操作去重与稳定分页 |
| `TaskState` / `diary_data` | 唯一当前正文与归档；读写统一排队和事务 |
| `diary_version:{date}:{sha256}` | 日期与原始正文生成内容地址；完整正文快照 |
| `diary_versions:{date}` | 内容去重索引；不自动裁剪竞争正文 |
| `diary_operation:{operationId}` | 原始载荷指纹和已提交回执；相同 ID 不同载荷返回 400 |
| `POST /api/diary/sync` | 按原日期保存，自动合并或保全版本，返回提交证明与规范正文 |
| `GET /api/diary/versions?date=&cursor=` | Bearer 认证读取，每页 20 条；从最旧侧计数的游标避免新版本插入导致分页跳项 |
| Apple `DiaryDraftState / WorkspaceService / WorkspaceStore` | 持久化操作、校验回执、较晚输入和账户隔离；原生版本历史 |
| Web `features/diary/` | 按连接与 Tab 隔离的草稿、串行请求、自动重试、版本恢复 |
| Mini `features/diary/` 与 `utils/diary-sync.mjs` | 页面所有权、全局写队列、原文基线、回执与草稿接管 |
| Mini `pages/diary-versions/` | 查看、分页、恢复；失败的恢复保留原操作 |

JavaScript 两端共享操作与回执契约；合并规则只在服务端实现，不维护三套算法。原 CAS 及遗留接口在支持事务的后端修改正文时也记录前后版本，元数据更新不产生正文副本。

历史按不同正文去重，不是每次按键的审计日志；相同正文再次出现复用已有版本 ID 与首次记录时间。版本及去重回执目前不自动删除，应观测存储增长，再单独设计明确的保留与导出策略，不因清理空间悄悄删掉另一端的修改。大型全文比较超过预算时保全双方，不扩大同步 CPU；完整历史仍按需分页读取。

## 2026-10-07 客户端同步竞态修复

按顺序复现并修复五项问题，使用合成正文和任务，没有向真实业务库写入测试数据。

1. 小程序将正文保存、回执确认、后续基线推进纳入同一控制器队列；操作开始时才生成载荷。较晚输入即时落本机，丢回执的旧操作先按原 ID 和完整载荷重放，再提交较晚正文。下一基线仍是提交原文，不能采用包含其他端文字的合并回执。
2. 版本恢复通过保存协调器等待当前草稿的完整保存过程，而不只等待 POST。所有日期的未确认草稿都受保护；有活动编辑器时先自动保存，失败或没有可确认保存的旧进程草稿时拒绝替换。自身恢复操作仍可按原 ID 重试。
3. 小程序版本接口缺失、网络失败或无有效 revision 时，使用经过原鉴权的业务只读接口检查更新；401/403 单独呈现，不以其他接口绕过认证失败。完整读取失败不确认版本，恢复后自行清除提示；上海日记日与自然日变化也触发检查。错误提示在页面内显示，周期失败不反复弹窗。
4. 任务读取以请求开始的修改版本、各任务的写入版本和待提交状态判断哪些条目需保留，其他任务仍接收远端变化；真正更晚的服务端任务时间戳可被接受。采用校验过的服务器任务回执，不把表单快照当作成功凭据；已卸载页面不回写缓存。
5. 网页验证云端数据后，恢复所有日期的草稿保存；各日期独立保留重试计时器，重复刷新和今天继续输入不会使历史草稿长期等待。自动版仍走原服务端三方合并，旧版 CAS 冲突保护保留，清空与首次上传旧日期均验证。
